# 그레이박스 맵 (조감 3/4 시점)

레퍼런스 게임 영상의 **카메라와 픽셀 격자**를 재서, 같은 시점으로 회색 상자(그레이박스¹) 테스트 맵을 pixel-splat 엔진에서 그린다.
캐릭터는 스킨 없는 마네킹(BB, `examples/soldier ... --outfit none`)을 그대로 세워 크기를 맞춘다.

```
layout.json ──level.py──▶ height(x,z) · surface(x,z)        게임 로직이 묻는 것 (땅 높이, 밟은 재질)
                      └──▶ splats() ─▶ SplatModel            그리는 것 (학습 없음)
            ──graybox.py build──▶ 레벨 전체 G-buffer 1장 + 해 그림자 맵  (out/map_45/level_bake.npz)
            ──graybox.py render / clip / compare──▶ PNG · MP4 · GIF
```

## 실행

```bash
cd pixel-splat            # venv 활성화 상태, PYTHONPATH=.
python examples/map/graybox.py build             # 1~2분 (splat 17만 개, CPU 4코어) → out/map_45
python examples/map/graybox.py render            # overview.png, view_bb.png, bb_closeup.png (5~15초)
python examples/map/graybox.py clip              # walk_follow.mp4 / .gif (프레임당 0.5~0.9초, 371프레임)
python examples/map/graybox.py compare --ref-video <레퍼런스.mp4> --ref-time 15
```

굽는 폴더는 **카메라마다 따로**다: 기본(45°)은 `out/map_45`, `--elev 30`이면 `out/map_30`. 다른 폴더는 `-o`로 고른다(render·clip·compare도 같은 `-o`).
이미 **다른 카메라로 구운** 폴더에 `build`하면 덮어쓰지 않고 멈춘다(바꾸려면 `--force`). 예전 30° 결과가 있는 `out/map`은 그대로 남는다.
내려다보는 각 `--elev`는 5~85°만 받는다(0°는 땅이 안 보이고 해 방향 계산이 0으로 나뉜다).

BB는 `out/bb`(60k splat)를 읽어 1,000개로 솎고 그만큼 키워 쓴다. 인물이 6×16픽셀이라 splat이 전부 래스터 타일 몇 칸에 몰리는데,
래스터 비용은 타일당 splat 수에 비례한다(60k 그대로면 프레임당 10초 이상, 1,000개면 0.5초, 이 크기에서는 그림이 같다). 다른 폴더면 `--bb`.
BB 색은 기본이 단색(따뜻한 점토색)이다. 구울 때의 색을 쓰려면 `--bb-color own`.

## 맵 고치기: `layout.json`

길이는 전부 **미터**, `x` = 동쪽, `z` = 남쪽(카메라 쪽), 높이는 풀밭 기준. 각도는 도(°)이고 +x에서 +z 쪽으로 돈다.
월드 단위는 soldier와 같다(1.80 단위 = 1.75 m, 땅 y = −1). 변환은 `level.UNITS_PER_M`.

| `type` | 뜻 | 값 |
|---|---|---|
| `hill` | 완만한 언덕 | `at`, `radius`, `height` |
| `pond` | 평평하게 꺼진 연못(어두운 면) | `at`, `radius` [rx, rz], `depth`, `bank`(기슭 폭) |
| `plateau` | 절벽으로 둘러싸인 단 | `at`, `size` [가로, 세로], `height`, `rot` |
| `ramp` | 경사로 | `at`, `size` [길이, 폭], `rot`(오르는 방향), `height` [시작, 끝] |
| `path` | 길(땅에 칠한 띠) | `points` [[x,z]…], `width` |
| `spawn` | 스폰 표시(원판 + 바라보는 방향) | `at`, `facing` |
| `rock` | 바위(반 타원체) | `at`, `size` [가로, 높이, 세로], `rot` |
| `tree` | 나무 대역(원기둥 + 원뿔/구) | `at`, `height`, `radius`, `canopy` = `cone`\|`sphere` |

`demo` 항목은 렌더용이다: `stand`(BB가 서는 곳), `walk`(걷는 경로·속도), `compare`(비교 그림에서 서는 곳).
고친 뒤에는 `build`부터 다시 돌린다. 색은 재질과 높이로만 정한다(`level.TONE`, 걸을 수 있는 땅은 1 m 오를 때마다 조금 밝게).
바닥의 눈금은 1 m(굵은 선 5 m)이고 픽셀마다 월드 좌표로 그려서 항상 1픽셀 폭이다. 선의 반폭은 그 픽셀이 덮는 땅의 반이고,
픽셀의 법선으로 계산하므로 경사로·언덕에서도 1픽셀이다(평지 값 하나로 그리면 카메라 쪽 경사로에서 선이 절반쯤 2픽셀이 된다).
x = 0 선은 원점이 픽셀 **모서리**에 고정되어 있어 두 픽셀 한가운데를 지난다. 예전에는 양쪽 픽셀이 둘 다 선으로 칠해져 이 선만 2픽셀이었다
(`out/map_45`: 277·278열이 둘 다 0.74배). 이제 선의 띠를 한쪽만 닫힌 구간으로 두고 음수 쪽으로 아주 조금(반폭의 0.1%) 밀어서,
경계에 걸친 선은 늘 음수 쪽 픽셀 하나만 칠한다(`out/map_45b`: 277열만 0.736배, 41줄 모두 1픽셀).

**`layout.json` 검사.** `build`(그리고 `Level`을 만드는 모든 곳)는 먼저 파일 전체를 검사하고, 틀린 곳을 **한꺼번에** 한국어로 알려 준다 —
몇 번째 요소(`elements[3] (4번째, pond 'pond')`)의 어느 값이 무엇이어야 하는지, 지금 값은 무엇인지. 예:

```
layout.json에 고칠 곳이 2개 있습니다:
  - elements[0] (1번째, hill 'west_rise'): 'radius' 값이 없습니다 — 0보다 큰 숫자를 넣어 주세요
  - elements[5] (6번째, pond 'pond'): 'radius'는 0보다 큰 두 숫자 [a, b](미터)여야 합니다 (지금: 4)
```

잡는 것: 빠진 값, 모양이 틀린 값(쌍 자리에 숫자 하나 등), 0 이하인 크기·높이(음수 `height`의 plateau 포함), 모르는 항목(`"rotation": 45` → "혹시 'rot'?"),
모르는 종류, 맵(`size`) 밖으로 나가는 요소(나무·바위는 반지름까지, plateau·ramp는 돌린 네 모서리까지), 줄기 자리가 없는 구형 나무, `demo`의 맵 밖 점, JSON 문법 오류(몇째 줄).
겹친 언덕은 높이가 **더해지므로** 카메라가 담는 상자(`bounds_world`)도 이제 실제 땅 높이에서 잰다(예전에는 가장 높은 언덕 하나만 봤다).

## 카메라 측정 (레퍼런스 영상 1848×1080, 60 fps, 44.5초)

| 항목 | 값 | 어떻게 쟀나 | 확실한 정도 |
|---|---|---|---|
| 아트 픽셀² 크기 | 영상 8.745 px | 가로·세로 경계 밝기차의 주기(푸리에) — 5개 프레임에서 같은 값 | 측정 |
| 한 화면 | 211.3 × 123.5 아트 픽셀 | 1848/8.745, 1080/8.745 | 측정 |
| 투영 | **직교**(원근 없음) | 카메라가 움직일 때 화면 위쪽 띠와 아래쪽 띠의 땅 흐름 비 = 1.0000 (사분위 0.9988~1.0011, 1,080개 구간). 세로 화각 10°의 원근만 있어도 1.09~1.18이어야 한다 | 측정 |
| 격자 | 월드에 고정 | 격자 위상이 프레임마다 바뀐다 = 저해상도 그림을 통째로 서브픽셀 이동(부드러운 스크롤) | 측정 |
| 내려다보는 각 | **45° (정한 값)** | 측정으로는 정해지지 않았다: 땅 위 단서는 25~36°, 단서 하나는 44~45°(아래 "각도"). 그중 **45°를 쓰기로 정했다**. 30°도 옵션으로 남긴다 | 선택 |
| 사람 크기 | 선 사람 ≈ **16 아트 픽셀** (몸통 폭 6~7) | 15초 프레임의 선 캐릭터(머리 끝~발) | 측정(1프레임), 캐릭터 실제 키는 모름 |
| 배율 | **11.1** 아트 픽셀 / 월드 단위 (11.42 px/m) | 1.75 m BB가 45°에서 대략 16픽셀(가끔 15)이 되도록 맞춤 — 렌더로 확인(아래 "배율") | 위 둘에서 유도 |
| 보이는 땅 | 가로 18.5 m × 깊이 15.4 m | 211/11.42, 124/11.42/sin45° | 유도 |
| 해 | 그림자는 화면 왼쪽 + 약간 아래로, 길이 ≈ 화면에서 기둥 키의 0.89배 | 15초 프레임의 선 캐릭터 그림자(약 12×2 픽셀) | 추정 |

30°로 그리려면 `build --elev 30`(배율은 맞춰 둔 9.6이 저절로 붙는다: BB 16픽셀, 9.87 px/m, 한 화면 21.4 m × 25.1 m; 결과는 `out/map_30`).
30°·45° 말고 다른 각을 주면 두 값 사이를 직선으로 어림한 배율을 쓰고 경고를 낸다 — 잰 값이 아니므로 `render` 뒤 `render.json`의 `figure_px`를 보고 `--px-per-unit`으로 맞춘다.

**배율**³: 선 BB는 같은 키의 막대보다 화면에서 크다. 몸의 앞뒤 두께가 sin(각)만큼 더 보이기 때문인데, 45°에서는 그 몫이 30°보다 크다.
그래서 cos 비율로 옮긴 값(9.6 × cos30°/cos45° = 11.8)이나 앞서 적어 둔 11.3은 크다 — 11.3은 렌더하면 **17~18픽셀**이다.
BB가 서는 자리의 소수 픽셀 위치에 따라 1픽셀씩 달라지므로 12곳(서브픽셀 위치를 고르게)에서 쟀다(평평한 땅, `figure_height_px`):

| 각 | 배율 | BB 키(픽셀), 12곳 (모두 facing 90) | 평균 |
|---|---|---|---|
| 30° | 9.6 | 16 ×9, 17 ×3 | 16.25 |
| 45° | 10.4 | 15 ×10, 16 ×2 | 15.17 |
| 45° | 10.6 | 15 ×9, 16 ×3 (데모 자리는 16) | 15.25 |
| 45° | 10.8 / 10.9 | 15 ×5, 16 ×7 | 15.58 |
| 45° | 11.0 | 15 ×1, 16 ×11 | 15.92 |
| 45° | **11.1** | **16 ×12** | **16.00** |
| 45° | 11.2 | 16 ×9, 17 ×3 | 16.25 |
| 45° | 11.3 | 17 ×11, 18 ×1 (데모 자리는 18) | 17.08 |

11.1은 12곳 모두 16픽셀이고 양옆(11.0, 11.2)도 거의 16이라 가운데 값으로 골랐다. 10.6은 데모 자리 한 곳에서만 16이고 대부분 15다.
위 12곳은 모두 한 방향(facing 90)이다. 자리와 방향을 섞어 25가지로 다시 재면 11.1에서 **16픽셀 21번, 15픽셀 4번**이었다
(15는 몇몇 자리에서 facing 90과 270). 그래서 정확히는 "**대략 16, 가끔 15**"픽셀이다.
`out/` 없이도 도는 테스트(`test_mannequin_extremes_span_about_16_px_at_the_calibrated_cameras`)는 BB 쉬는 자세의 끝점 12개(정수리·뒤통수·발끝·뒤꿈치)를
투영해 화면 높이를 잰다: 45°/11.1에서 8방향 평균 15.41(14.83~15.94; 실제 렌더는 여기에 splat 크기가 더해져 15~16픽셀).

**각도**: 직교 카메라에서는 땅 위의 원이 세로로 sin(각) 만큼 눌려 보인다. 그 눌림을 네 가지로 쟀는데 서로 꼭 맞지는 않는다.

| 단서 | sin(각) | 각 |
|---|---|---|
| 곰이 방향을 바꿀 때 실루엣의 가로 분산 대 세로 분산의 기울기(타원체 근사) | 0.41~0.55 | 25~33° |
| 곰의 땅 위 속도(화면 속도 + 땅 흐름) 분포를 가장 뾰족하게 만드는 값 | 0.59 (군집별로는 0.38~0.58) | 36° (22~35°) |
| 땅에 떨어진 핏자국 분포의 세로/가로 폭 | 0.44~0.48 (초반 작은 무리는 0.6~0.7) | 26~29° |
| 플레이어 질주 속도가 모든 방향에서 같다고 볼 때(카메라 속도의 바깥 테두리) | 0.70 | 44° |

땅 위 단서 세 가지는 25~36°에 모이고, 플레이어 속도 단서는 44°를 가리킨다. 측정만으로는 어느 쪽인지 정할 수 없어서
**45°를 기본값으로 쓰기로 정했다**(측정 결과가 아니라 선택이다). 30°는 `--elev 30 --px-per-unit 9.6`으로 그대로 쓸 수 있다.
레퍼런스가 어떤 엔진으로 만들어졌는지는 알 수 없다.

## 왜 이렇게 만들었나

- **레벨은 학습하지 않는다.** 요소가 전부 수식으로 된 단순한 모양이라 splat을 표면에 **격자로** 직접 놓는다(중심·법선·크기가 수식에서 나온다).
  섞지 않는(hard) 합성은 splat 중심에서 1.41σ 안쪽만 덮는데, 격자 간격 d에 σ = 0.62d면 빈틈이 없다(테스트로 확인).
  같은 조건을 무작위 표본(`SplatModel.from_mesh`)으로 채우려면 splat이 약 5배 필요하다.
- **레벨 G-buffer는 한 번만 그린다.** 직교 카메라는 정수 픽셀만큼 옮겨도 같은 픽셀이 그대로 밀릴 뿐이라(테스트로 확인),
  레벨 전체를 월드에 고정된 격자로 한 장 구워 두고 프레임마다 창만 잘라 쓴다. 카메라가 흘러도 **배경은 절대 자글거리지 않고**
  프레임 비용은 BB와 조명뿐이다. 남는 소수 픽셀은 확대한 뒤에 옮긴다(레퍼런스와 같은 방식).
- **엔진 코드를 그대로 쓴다**: `rasterize`(큰 그림은 256px 조각으로 나눠 호출), 2× 렌더 + 투표(`select_downsample`), `despeckle`,
  `shade` / `postprocess`, `ShadowMap` + `visibility`, BB는 `render_gbuffer_frame`(Almost Pixel Perfect snapping 포함).
  예제에서 따로 한 것은 둘이다: 외곽선(엔진의 깊이차 기준은 낮은 각도로 본 땅 전체에 선을 긋는다 → 접평면 거리 기준),
  SSAO 반경(엔진 기본값은 2단위짜리 모델용 → `gbuf.ssao`를 장면 크기로 호출).

## 벽

해가 화면 오른쪽 조금 뒤에서 비추므로 **카메라 쪽을 향한 절벽 면에는 해가 닿지 않는다**. 하늘빛도 절반만 받아서 예전에는 거의 검었다:
중간값 (34, 35, 41) — 배경 (19, 19, 28)과 거의 같아서 벽이 세상에 뚫린 구멍처럼 보였다. 실제로는 앞의 밝은 풀밭에서 튄 빛이 벽을 비춘다.
그 반사광(`graybox.WALL_BOUNCE` = 0.45, 해의 색 × 재질 색 × 면이 선 정도)을 **절벽 픽셀에만** 더했다. 다른 픽셀은 한 값도 바뀌지 않는다(테스트).

| `out/map_45b` 전체 그림, 중간값 sRGB | 예전 | 지금 |
|---|---|---|
| 카메라 쪽 절벽 면 (4,904픽셀) | (34, 35, 41) | **(75, 75, 81)** |
| 배경 | (19, 19, 28) | (19, 19, 28) |
| 그늘진 풀밭 | (88, 92, 105) | (88, 92, 105) |
| 해 받는 풀밭 | (177, 177, 177) | (177, 177, 177) |
| 나무 줄기 | (25, 26, 30) | (25, 26, 30) |

벽은 이제 배경보다 확실히 밝고 그늘진 땅보다는 조금 어둡다(0.3이면 62, 0.6이면 87 — 그늘진 땅과 같아져 높이차가 덜 읽힌다).

## 맵을 짤 때 알아둘 것 (이 카메라의 성질)
- 높이 h인 물체는 **뒤(북쪽) 땅을 h × 1.0 만큼 가린다**(45° 기준, h / tan 45°; 30°였다면 h × 1.73). 5 m 나무는 뒤쪽 5 m를 덮는다.
  그래도 싸움터 남쪽에는 키 큰 것을 두지 않는 편이 좋다(30°로 그릴 때 데모 지점이 나무에 두 번 가려져 나무를 옮겼다).
- 화면 세로 1픽셀이 땅에서는 1.41픽셀 거리다(가로 11.42 px/m, 깊이 방향 8.07 px/m; 30°라면 2배). 깊이 방향 길·틈은 가로보다 1.4배 넓게 잡아야 같은 굵기로 보인다.
- 해는 레퍼런스 화면에서 읽은 **그림자 모양**(기둥 그림자가 화면에서 기둥 키의 0.89배 왼쪽, 0.08배 아래)으로 정해 두고,
  각도에 맞는 해 방향을 거기서 계산한다(30°: 고도 52°·방위 100°, 45°: 고도 57.7°·방위 97.1°). 각도를 바꿔도 그림자가 화면에서 같은 모양이다.

## 밀도 ×3 (`--density 3`, 극세 픽셀)

`graybox.py build --density 3`은 같은 카메라(45°)를 **아트 픽셀²을 세 배 촘촘하게** 굽는다: 33.3 아트 픽셀/단위(34.25 px/m), BB 약 48픽셀, 한 화면(633×372)은 여전히 18.5 m × 15.4 m.
결과 폴더는 `out/map_45x3`(기본 폴더 이름에 `x3`이 붙어 ×1과 섞이지 않는다). ×1(`--density 1`, 기본)은 예전과 픽셀 하나 다르지 않다(테스트).

아트 픽셀로 맞춰 둔 값은 밀도에 따라 같이 바뀌고, 월드 단위로 맞춘 값(깊이 허용치, SSAO 반경 0.6, 외곽선 판정 0.16)은 그대로다:

| 무엇 | ×1 | ×3 | 왜 |
|---|---|---|---|
| splat 격자 간격 | 0.125 m | **0.0417 m** (153만 splat) | 격자 한 칸이 아트 픽셀 1.4개가 되게(×1과 같은 비율). 0.125 m 그대로면 splat의 둥근 테두리가 고원·경사로 가장자리에 점선 톱니로 보이고 원뿔 나무가 각진다. 0.0625에서도 고원 옆면 톱니가 남았다 |
| 해 그림자 맵 | 1024² | **3072²** (텍셀 0.021 단위 = 0.7 아트 픽셀) | 텍셀이 아트 픽셀보다 작아야 그림자 가장자리가 계단지지 않는다 |
| SSAO⁴ 고리 반경 | 3 px | 9 px | 같은 땅 넓이를 본다 |
| 가장자리 여유(guard) | 4 px | 12 px | SSAO 고리보다 넓어야 창을 옮겨도 가장자리 픽셀이 바뀌지 않는다 |
| 눈금·외곽선 굵기 | 1 px | **1 px** | 아래 |
| BB splat | 1,000 | 9,000 | 덮는 픽셀이 9배; 적으면 실루엣이 울퉁불퉁 |
| BB 자기 그림자 splat / 맵 | 350 / 96² | 1,050 / 96² | 그림자는 실루엣만 필요; 192²·288²는 평지에서 같은 그림자를 5–9배 시간에 그렸다 |

**눈금선은 1픽셀로 두었다.** ×3에서 3픽셀 선은 땅 위 9 cm 띠가 되어, 촘촘해진 그림 위에서 ×1의 굵은 격자를 그대로 확대한 것처럼 보인다 — "더 극세 픽셀"이라는 결정과 반대다.
1픽셀 선은 휴대폰에서 CSS 1픽셀(기기 3픽셀)이라 땅 밝기의 0.90·0.74배 선으로 충분히 보인다(스크린숏). 외곽선도 같은 이유로 1픽셀.

**BB를 그리는 창을 몸에 딱 맞췄다.** 엔진의 래스터라이저는 창의 픽셀 × 타일당 슬롯 수만큼 일한다. 예전에는 몸 둘레의 고정 정사각형(×3에서 98×98)을 그렸는데,
이제 splat들의 화면 상자(3σ) + 3픽셀만 그린다. 그림은 픽셀 하나 다르지 않고(테스트) ×3에서 한 프레임 4.1초 → 0.4초. 타일 슬롯도 처음부터 512로 시작해 넘쳐서 다시 그리는 한 번을 아낀다.

**알려진 그림 문제**(예전부터 있던 것, ×3에서 더 잘 보임): 연못 북쪽 기슭 일부에 해 그림자 줄무늬(그림자 맵 acne)가 보인다. 바이어스·법선 오프셋을 바꿔도 남아서 고치지 않았다.

## 플레이 빌드 (브라우저에서 BB 걸고 뛰고 원투)

`play.py`가 구운 레벨과 BB를 **브라우저 한 화면짜리 게임**에 필요한 파일로 내보낸다(라이브러리 없이 canvas 2D). 맵과 같은 카메라(45°, 직교, 월드 고정 격자)에서
BB가 걷고, 빠르게 뛰고, 가져온 원투를 한다. 지금 빌드는 **×3 밀도**다.

```bash
python examples/map/graybox.py build --density 3                       # 레벨 굽기 → out/map_45x3 (약 6분)
python examples/map/play.py build                                      # → out/play4 (기본: --bake out/map_45x3, --onetwo out/onetwo4/5m/clip.npz)
python examples/map/play.py build --only level,page                    # 스프라이트는 두고 다시 (몇 초)
python examples/map/play.py check -o out/play4                         # manifest와 파일이 맞는지
python examples/map/moves.py report                                    # 이음매마다 관절이 한 프레임에 몇 도 튀는지
```

지금 빌드는 `out/play4`다: 레벨은 `out/play3`과 바이트까지 같고, 스프라이트는 빠른 멈춤 클립이 늘었고, 페이지를 고쳤다(아래 "움직이는 중 원투"와 "페이지가 하는 일"의 두 층 맞춤, 합성, 프레임, 이동, 조작). `out/play3`은 비교용으로 그대로 둔다.
크기 **10.26 MB**(`sprites.webp` 4.40 MB, `sprites_data.png` 4.50 MB, `level_depth.png` 605 KB, `level.png` 283 KB, `manifest.json` 172 KB, `index.html` 43 KB, `sun.png` 5 KB, `terrain.png` 8 KB).
스프라이트 5,952장(8방향 × 744) 중 다른 그림 5,366장, 아틀라스 4096×3851. 처음부터 그리면 약 48분(프로세스 4개, 이 4코어 기계; 프레임당 약 0.5초 몫).
방향을 16개로 하면 크기가 약 2배(약 20 MB)로 15 MB 예산을 넘고, 아틀라스도 iOS Safari가 읽어 들이는 캔버스 한도(1,670만 픽셀)를 넘어 두 장으로 나눠야 해서 8개로 두었다.

스프라이트는 프로세스 4개(`--workers`)가 방향을 나눠 그리고, 그린 프레임은 `out/play4_sprite_cache.pkl.gz`에 남겨 **자세가 같은 프레임은 다시 그리지 않는다**(모션 하나만 고치면 그것만 다시).
이 캐시는 `out/play3_sprite_cache.pkl.gz`를 복사한 것이라 play4는 빠른 멈춤 1,840장만 새로 그렸다(빌드 14분). 진행은 `out/play4_render.log`. 예전 ×1 빌드 `out/play`는 그대로 남아 있다(`--bake out/map_45b -o out/play`로 다시 만들 수 있지만 새 페이지·모션으로 만들어진다).

| 파일 | 내용 | 인코딩 |
|---|---|---|
| `level.png` | 레벨 전체 그림(눈금·그림자·AO·외곽선), ×3: 1652×1209 | sRGB PNG |
| `level_depth.png` | 픽셀마다 카메라 깊이 + 두 플래그 | R·G = 16비트 깊이, B = 128(해) \| 64(걸을 수 있는 땅·물) |
| `sun.png` | **땅 자체의** 해 받음, 6.25 cm 칸마다 (768×640) | R ≥ 128 = 해 |
| `terrain.png` | 0.25 m 칸마다 땅 높이 + 걸을 수 있는지 (192×160) | R·G = 높이 mm + 32768, B = 255 걸을 수 있음 |
| `sprites.webp` | BB 프레임(투명 배경), 8방향, 같은 프레임은 한 번만 | **무손실 WebP**⁵(PNG의 약 절반; 브라우저가 바이트 그대로 푼다 — 테스트) |
| `sprites_data.png` | 같은 사각형: 픽셀 깊이 − 발 딛은 점의 깊이, 그림자 | R·G = 깊이차 × 512 + 32768, B = 255 그림자; 반드시 PNG |
| `manifest.json` | 카메라, 파일, 인코딩, 프레임 사각형·기준점, 애니메이션 | JSON |

**모션 (`moves.py`, 전부 60 fps).**

| 이름 | 종류 | 프레임 | 내용 |
|---|---|---|---|
| `idle` | loop | 120 (2 s) | 원투의 첫 자세(가드) 둘레로 숨쉬기 (`motion.guard_idle_rots`) |
| `walk` | 걸음 loop | 48 = 0.8 s = 1.12 m | 1.4 m/s에서 프레임마다 한 장, 겹치거나 건너뛰는 프레임 없음 |
| `run` | 걸음 loop | 40 = 0.667 s = 2.5 m | 3.75 m/s, 체공 있음 (`motion.run_gait_rots`) |
| `onetwo` | 동작 | 144 (2.4 s) | 손목 범위 "human" 가져오기(`out/onetwo4/5m`). 마지막 0.5초는 가드로 돌아오며 끝남 = idle 첫 프레임 |
| `start` | 전환 | 24 | idle → walk (뒷발인 오른발부터) |
| `stopA` / `stopB` | 전환 | 24 / 30 | walk → idle, 걸음 위상 0(왼발이 앞에 막 디딤) / 0.5(오른발 앞: 한 걸음 더 가서 왼발이 앞으로) |
| `w2r_0`·`w2r_5` / `r2w_0`·`r2w_5` | 전환 | 20 | walk ↔ run, 위상 0 / 0.5 (두 loop는 같은 위상을 쓴다: 0 = 왼발 디딤) |
| `qw0`–`qw3` / `qr0`–`qr7` | 빠른 멈춤 | 16–31 | 걷기(위상 j/4)·달리기(j/8) 중 J → 원투로 바로. 아래 "움직이는 중 원투" |

스텝 인·아웃은 뺐다(K 키, 버튼, 아틀라스 모두).

**전환을 렌더링해 둔 이유.** 스프라이트는 실행 중에 섞을 수 없으니, 자세가 바뀌는 곳은 (1) 거의 같은 자세 사이의 컷이거나 (2) 미리 그린 전환 클립이어야 한다.
idle과 원투는 같은 가드 자세를 공유해서(1)로 잇고, 걷기·달리기처럼 다리가 다른 곳에 있는 동작 사이는 (2)로 잇는다.
전환 클립은 두 동작을 시간대로 재생하며 섞고(관절 slerp, 골반 lerp, smootherstep), **디딘 발에서 몸의 이동을 뽑아**(발이 미끄러지지 않게) 그 값을 프레임별 `advance` [앞, 왼쪽](m)로 manifest에 넣은 뒤,
디딘 발을 바닥에 핀으로 고정한다(`motion.pin_legs`). 페이지는 걸음 loop가 위상 0이나 0.5의 프레임(진입 프레임)을 **보여 준 다음** 화면 프레임에 전환의 0번(진입 프레임 바로 다음 자세)을
보여 준다(걷기에서 최대 0.4초 기다림). 그 프레임에서 BB는 걸음으로 진입 자세까지만 가고 나머지는 전환의 `advance`로 간다.

| 관절이 한 화면 프레임 사이에 가장 크게 바뀐 각도 | 예전 페이지 (30 fps, 바로 바꿈) | 지금 (60 fps, `moves.py report`) |
|---|---|---|
| 대기 → 걷기 시작 | 122.5° (왼쪽 아래팔) | 1.9° (컷) · 클립 안 10.3° |
| 걷기 → 대기 | 122.9° | 4.0° (컷) · 클립 안 9.5° · 끝 0.05° |
| 걷기·달리기 중 J | 122.9° | 빠른 멈춤으로 바로 원투: 컷 ≤ 12.8°(달리기 한 프레임 크기), 원투로 넘어갈 때는 원투 자신의 그 프레임 걸음과 같음 |
| 대기 → 원투 | 20.5° | 2.0° |
| 원투 끝 → 대기 | 18.1° | 0.08° |
| 걷기 ↔ 달리기 | (없음) | 컷 ≤ 4.9°, 클립 안 ≤ 11.7° |
| 참고: 동작 자체 | 걷기 loop 24.3°, 원투 76.1° | 걷기 10.3°, 달리기 12.7°, 원투 47.7° |

전환 클립에서 디딘 발이 미끄러지는 거리는 프레임당 최대 1.6 mm(아트 픽셀 하나는 29 mm).

위 "컷" 값은 페이지가 진입 프레임 다음에 전환 0번을 보여 줄 때의 값이다. **실제 페이지에서 잰 값**(60 Hz 타임스탬프로 돌리고 화면 프레임마다 보인 자세를 `moves.py`의 자세로 되짚음):
걷기 → 멈춤 3.9°, 걷기 → 달리기 3.9°, 달리기 → 걷기 12.7°(달리기 loop 한 프레임과 같은 크기), 대기 → 걷기 시작 0.1°, 시작 → 걷기 3.9°.
예전 페이지(play3)는 진입 프레임을 건너뛰어 8.7°·8.7°·16.4°였고, 그 프레임에 걸음 한 걸음과 `advance[0]`을 둘 다 더해 4.4 cm 갔다가 다음 프레임은 0 cm였다(지금 2.3 → 2.1 → 1.9 cm).

**움직이는 중 원투(빠른 멈춤).** 예전에는 걷거나 뛰다 J를 누르면 걸음이 위상 0·0.5에 닿기를 기다려 멈춤 클립을 다 하고, 원투가 처음부터(0.67초 가드 바운스) 시작해서
J부터 잽이 뻗기 시작할 때까지(앞손이 가드보다 5 cm 앞) 달리기 1.6–2.0초, 걷기 1.3–1.5초 걸렸다. 지금은 **빠른 멈춤** 클립(`qw0`–`qw3`, `qr0`–`qr7`)이 걸음에서 원투로 바로 간다:
- 들어가는 곳: 걷기 1/4 주기(12프레임)마다, 달리기 1/8 주기(5프레임)마다. 기다림 최대 0.2초 / 0.083초.
- 윗몸은 14프레임에 걸쳐 원투(바운스를 건너뛴 26번 프레임부터 시간대로 재생)로 섞이고 41번 프레임에서 잽이 나간다. 다리는 디딘 발이 가드의 앞발이 될 수 있는 위상
  (`moves.py quick-scan`으로 16분의 1마다 잰 결과: 걷기 0, 9–12, 15 / 달리기 3–13)부터 16프레임에 걸쳐 가드 자세로 들어간다. 그 전까지는 다리가 계속 걷거나 뛴다
  (다른 위상에서 바로 섞으면 디딘 발이 앞으로 가야 해서 몸이 최대 26 cm 뒤로 밀렸다).
- root 이동은 디딘 발에서 뽑고, 발이 안 디딘 동안(달리기 체공)은 다리의 섞임에 맞춰 걸음 속도에서 0으로 줄인다. 뒤로 가는 프레임은 최대 0.9 cm, 끝은 정지.
  원투의 잽 스텝이 섞이는 곳에서 한 프레임 앞으로 더 나가는 곳이 있다(달리기 `qr2` 최대 8.3 cm/프레임). 디딘 발 미끄러짐 최대 1.1 mm/프레임.
- 잰 값(실제 빌드, 60 Hz, 걸음 주기의 8곳에서 J): J → 잽이 뻗기 시작 **달리기 0.27–0.35초**(걷기→달리기 전환 중에 누르면 최대 0.43초), **걷기 0.27–0.42초**.
  걸음 → 빠른 멈춤 컷 ≤ 12.8°(달리기 loop 한 프레임 크기), 빠른 멈춤 → 원투는 원투 자신의 그 프레임 걸음과 같다.
- 연타: 원투 중에는 크로스가 가장 멀리 뻗은 다음 프레임(`chain_from`, 60번)부터 누른 J만 받아 **하나만** 기억하고, 원투가 끝나면 바로 다음 원투를 처음부터 한다
  (끝 자세 = 첫 자세라 컷 0.00°). 그 전에 누른 J는 버린다(연타가 쌓이지 않게). 빠른 멈춤 도중의 J도 버린다.
- 비용: 스프라이트 1,840장 추가 렌더링 13분(캐시에 있던 4,112장은 그대로), 아틀라스 4096×3851(1,577만 픽셀, iOS 한도 1,670만 아래), 빌드 전체 10.26 MB.

**페이지가 하는 일.**
- 화면: 아트 픽셀을 **기기 픽셀의 정수 배**로 키운다. CSS 픽셀당 아트 픽셀 `k = max(1, round(게임 영역 폭 / 700))`, 기기 배율 = round(k × devicePixelRatio).
  휴대폰(390×844, dpr 3): k = 1 → 아트 1픽셀 = CSS 1픽셀 = 기기 3픽셀, 가로 약 358 아트 픽셀 = **10.5 m**. 데스크톱(1280×800, dpr 1 또는 2): k = 2 → 기기 2 또는 4픽셀,
  가로 약 624 아트 픽셀 = 18.2 m(레퍼런스 한 화면과 같은 넓이).
- 그리기: 게임 영역은 두 층이다. **레벨 전체 그림 한 장**을 캔버스 하나에 그려 두고 카메라는 CSS transform⁶으로 옮기며(기기 픽셀 정수 단위라 정확, 브라우저 합성기가 처리해 프레임마다 다시 칠하지 않음),
  그 위에 **BB 상자만 한 작은 캔버스**를 얹는다: 그 상자의 레벨 픽셀에 그림자·가림·그늘을 합성한 것. 프레임마다 CPU가 채우는 것은 이 상자(×3에서 보통 51×53, 가장 큰 것 78×69)뿐이다.
  4배 CPU 감속(Playwright)에서 달리는 동안 프레임당 0.7–0.8 ms(95 % 1.4–1.6 ms), 원투 중 60 fps(휴대폰 390×844·데스크톱 1280×800 둘 다).
  예전처럼 화면 전체를 `putImageData`하면 같은 조건에서 10 ms(95 % 15 ms)였다.
- 두 층 맞춤: 게임 영역의 왼쪽 위 모서리를 **기기 픽셀⁷ 정수 위치**에 놓고(가운데 정렬이 dpr 2.625 가로 화면에서 160.125 기기 픽셀처럼 픽셀 중간에 떨어지면 두 캔버스가 서로 다른 픽셀로 반올림되어
  격자선이 BB 상자 가장자리에서 끊겼다), 캔버스는 제 크기 그대로 두고 transform의 `scale`로 키운다(CSS 폭을 `79 × 8/7`처럼 주면 레이아웃이 1/64 픽셀로 잘라 한 줄이 밀린다).
  BB 캔버스에는 투명한 1픽셀 테두리를 둔다(합성기가 확대한 층의 가장자리 픽셀을 살짝 흐리게 섞는다). 창 크기·방향·배율이 바뀌면 다시 맞춘다.
  dpr 1, 1.25, 1.5, 1.75, 2, 2.625, 3 × 세로·가로에서 두 층이 같은 위치에서 맞고 어긋남 0 %(실제 빌드 화면을 기기 픽셀로 찍어 비교; 테스트 기준 0.5 % 이하. 예전: 1.75와 2.625 가로에서 두 층이 서로 다른 위치에서 맞음, 같은 위치로 보면 최대 8.7 % 어긋남).
- 합성: BB 픽셀은 (발 딛은 점의 깊이 + 그 픽셀의 깊이차)가 레벨 깊이보다 가까울 때만 그린다. 여유는 **물체(나무·바위·절벽) 0.15단위, 발 높이의 땅 0.6단위** — 땅은 비탈·연못 기슭에서 발 앞으로 솟아도 BB를 가리지 않는다(예전에는 연못 남쪽 기슭에서 발이 잘렸다).
  "발 높이의 땅"은 그 레벨 픽셀을 카메라 식으로 되돌려 얻은 땅 높이가 BB가 선 땅 높이와 **0.3 m 안**인 곳이다(한 픽셀의 시선에서 발보다 dh 높은 땅은 발 앞 약 dh 거리에 있으므로, "발 앞 0.3 m 안의 땅").
  고원 꼭대기도 잔디라 땅인데, 예전에는 1.6 m 고원 바로 뒤에 선 BB의 어깨·팔이 그 꼭대기 위에 그려졌다(전 맵 훑기: 292곳, 방향까지 967쌍). 지금은 0쌍이고 머리만 넘어 보이며, 연못 기슭의 발은 그대로 다 그려진다.
- 그늘: BB가 선 **땅 자체가 해를 받는지**(`sun.png`)로 정한다. 예전에는 발 픽셀을 덮은 것(나무 꼭대기일 수 있음)의 해 플래그를 읽어 431칸이 틀렸다.
- 프레임: 화면 프레임마다 "시간이 4분의 1프레임 앞서 도달한" 프레임을 보여 준다. `floor(시간 × 60)`으로 하면 60 Hz 화면의 시각이 프레임 경계에 딱 걸려서,
  rAF⁸ 시각의 흔들림(16.7, 16.7, 16.6 ms)만으로 한 프레임을 두 번 보이고 다음을 건너뛰었다(원투 2.4초에 24번 반복·23번 건너뜀). 지금은 60 Hz에서 반복·건너뜀 0, 120 Hz에서는 모두 두 번씩, 30 Hz에서는 하나 걸러.
  걸음은 간 거리로 프레임을 고르는데, 전환에서 위상이 프레임 사이로 들어와도 화면 프레임마다 정확히 한 장씩 넘어가도록 맞춘다.
- 이동: 위 = 북쪽, 초속 1.4 m(걷기) · 3.75 m(Shift 또는 스틱 80 % 넘게). 방향은 8개, 45°씩 50 ms 간격으로 돈다(반대로 돌아도 한 번에 뒤집히지 않음).
  스틱을 덜 밀면 그만큼 느리게 걷고(걸음 길이는 그대로, 걸음이 느려짐), **전환 클립도 같은 비율로 느리게 재생**해서 시작·멈춤에서 속도가 튀지 않는다(예전: 0.6 m/s로 걷다가 시작·멈춤 동안 약 1.2 m/s).
  자세와 이동이 함께 느려지므로 발이 미끄러지지 않는다. 스틱을 놓으면 놓기 전 속도로 멈춘다.
  크게 방향을 틀 때는 몸이 돌아갈 때까지 속도를 줄인다: 가려는 방향과 몸이 보는 방향의 차이에서 22.5°(8방향이라 피할 수 없는 몫)를 뺀 각의 cos배, 112.5°를 넘으면 0.
  D → A로 뒤돌면 약 0.1초 서서 몸을 돌리고(다리도 같이 멈춤: 걸음은 간 거리를 따라가므로), 90° 돌았을 때 38 %, 45° 남았을 때 92 %로 출발한다.
  등을 진 채(90° 넘게) 움직인 거리: 걷기 0.09 m → 0, 달리기 0.25 m → 0 (예전 페이지 같은 측정).
  칸을 대각선으로 넘을 때는 지나는 두 칸도 걸을 수 있어야 한다(바위 둘이 모서리로 맞닿은 틈으로 못 들어감; `play.reachable`과 같은 4방향 연결).
- 원투: 몸의 앞뒤 이동(최대 18.6 cm 런지)은 **스프라이트 안에** 그려 두었다. 페이지에서 BB의 자리는 그대로라 벽에서 이동이 한쪽만 막혀 누적되는 일(예전: J 열 번에 0.12 m)과,
  기준 픽셀이 바뀌며 카메라가 1픽셀씩 흔들리던 일(예전: 2.4초에 6번)이 없다. 클립의 처음과 끝 root는 같다(끝 0.5초를 가드로 되돌림).
- 조작: WASD·방향키 걷기, Shift 누른 채 달리기, J 원투(움직이는 중이면 빠른 멈춤으로 바로, 원투 끝 무렵 누르면 한 번 더). Ctrl·Cmd·Alt가 눌린 키는 브라우저 몫으로 둔다. 창이 가려지면(blur, visibilitychange) 누른 키를 놓는다.
  macOS는 Cmd를 누른 동안 뗀 키의 keyup을 보내지 않아 D가 눌린 채로 남을 수 있으므로, Cmd를 누르거나 뗄 때 누른 키를 모두 놓는다(계속 가려면 다시 누른다).
  터치: 화면 왼쪽을 누른 채 끌면 걷기, 끝까지(80 %) 밀면 달리기(손잡이가 주황색), 오른쪽 아래 원투 버튼.
- 오류는 화면에 보인다(프레임 루프의 예외, 빠진 애니메이션, 불러오기 실패). 프레임이 하나뿐인 동작도 된다.

확인: `tests/test_play_page.py`가 헤드리스 Chromium에서 페이지의 JavaScript를 실제로 돌린다(작은 레벨 + 빨간 카드 스프라이트): 충돌, 모서리, 경사로 높이,
나무 뒤 가림, 고원 꼭대기 뒤 가림, 땅으로 정하는 그늘, 비탈에서 발, 원투 열 번 뒤 위치·카메라(스프라이트 안 런지 포함), 걷기·달리기 속도와 전환, 터치 스틱(80 % 아래 걷기·위 달리기, 반만 밀 때 시작·멈춤 속도),
root 이동 부호와 이음매에서의 연속, 60·120·30 Hz에서 프레임 반복·건너뜀, 진입 프레임 다음 컷, 움직이는 중 J(빠른 멈춤), 원투 연타(하나만 기억), 뒤돌기에서 뒷걸음 없음, Cmd와 보조 키, dpr 7가지 × 세로·가로(+ 돌리기)에서 두 층 맞춤, 오류 표시, 한 프레임 동작, 포커스 링, 터치 안내 대비, 아틀라스 바이트.
페이지의 rAF를 테스트가 직접 돌려(정확한 타임스탬프) 프레임마다 무엇을 보였는지 본다. `-m slow`는 실제 빌드(`out/play4`, `PLAY_BUILD`로 바꿈)에서 감사 지점(연못 기슭 발, 고원 뒤),
실제 원투의 런지, 실제 이음매의 각도·이동, J → 잽까지 시간(달리기 ≤ 0.35초, 걷기 ≤ 0.45초), 4배 CPU 감속 프레임 시간(페이지 자신의 일: 중앙값 < 1.5 ms, 95 % < 4 ms; 지금 0.5–0.8 / 1.4–1.8 ms)을 잰다.

## 한계
- BB는 16픽셀이라 걸을 때 픽셀이 조금씩 바뀐다(snapping으로 줄였을 뿐 없앨 수는 없다). 배경은 고정이다.
- 경사로·언덕 위에서 BB는 골반 위치의 땅 높이만 따라간다(양발이 각각 땅에 붙지는 않는다).
- 카메라 방위(`--az`)는 0만 눈으로 확인했다. 정확히 남쪽에서 볼 때 나무의 좌우 대칭 splat은 깊이가 같아 앞뒤 순서가 임의다(그림에는 영향 없음).
- 눈금·그림자 맵은 `build` 때 굽는다. 해 방향이나 격자를 바꾸면 다시 구워야 한다.
- 플레이 빌드: BB 그림자는 평지 가정(경사·턱에서는 어긋나거나 사라짐), BB가 레벨 그림자에 들어가면 몸 전체가 한꺼번에 어두워진다(부분 그늘 없음).
  방향은 8개뿐이다(16개면 도는 모습이 더 부드럽지만 아틀라스가 약 2배라 15 MB 예산을 넘는다). 원투는 멈춰 서서 한다(움직이는 중 J는 빠른 멈춤으로 0.3–0.4초 안에 잽; 걷기→달리기 전환 중에는 전환이 끝난 뒤라 조금 더 늦다).
  원투의 런지는 스프라이트 안에 있어서 벽·나무 앞에서도 몸이 최대 18.6 cm 앞으로 나갔다 돌아온다(가림은 깊이로 맞게 그려짐).

---
¹ **그레이박스(gray box, blockout)**: 텍스처 없이 회색 덩어리만으로 맵의 크기·동선·높낮이를 먼저 잡아 보는 단계.
² **아트 픽셀**: 확대하기 전, 저해상도 그림의 픽셀 한 칸.
³ **배율(px_per_unit)**: 월드 길이 1단위가 화면에서 몇 아트 픽셀인지. 카메라를 더 내려다보게(각도↑) 하면 서 있는 물체가 화면에서 짧아지므로, 사람을 같은 16픽셀로 두려면 배율을 키워야 한다.
⁴ **SSAO**(screen-space ambient occlusion): 화면의 깊이만 보고 오목한 곳(벽 밑, 바위 둘레)을 조금 어둡게 하는 계산. 둘러보는 고리의 반경이 픽셀 단위라 밀도에 맞춰 키운다.
⁵ **무손실 WebP**: 구글의 그림 형식. 손실 없이 압축하면 풀었을 때 원래 바이트와 똑같고, PNG보다 작다. 브라우저가 거의 다 읽는다(사파리 14 이상).
⁶ **CSS transform**: 이미 그린 그림을 다시 그리지 않고 화면에서 위치만 옮기는 방법. 그래픽 칩이 처리해서 거의 비용이 없다.
⁷ **기기 픽셀과 dpr**: 화면의 실제 점 하나가 기기 픽셀이다. 웹 페이지는 "CSS 픽셀"로 크기를 말하고, CSS 1픽셀이 기기 픽셀 몇 개인지가 devicePixelRatio(dpr)다. 요즘 안드로이드 폰은 2.625처럼 정수가 아닌 경우가 많아, 위치가 기기 픽셀 사이에 떨어질 수 있다.
⁸ **rAF**(requestAnimationFrame): 브라우저가 화면을 새로 그리기 직전마다 페이지를 불러 주는 장치. 60 Hz 화면이면 약 16.7 ms마다지만, 넘겨주는 시각은 16.6–16.7 ms처럼 조금씩 흔들린다.
