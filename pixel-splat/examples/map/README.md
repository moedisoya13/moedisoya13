# 그레이박스 맵 (조감 3/4 시점)

레퍼런스 게임 영상의 **카메라와 픽셀 격자**를 재서, 같은 시점으로 회색 상자(그레이박스¹) 테스트 맵을 pixel-splat 엔진에서 그린다.
캐릭터는 스킨 없는 마네킹(BB, `examples/soldier ... --outfit none`)을 그대로 세워 크기를 맞춘다.

```
layout.json ──level.py──▶ height(x,z) · surface(x,z)        게임 로직이 묻는 것 (땅 높이, 밟은 재질)
                      └──▶ splats() ─▶ SplatModel            그리는 것 (학습 없음)
            ──graybox.py build──▶ 레벨 전체 G-buffer 1장 + 해 그림자 맵  (out/map_45/level_bake.npz)
            ──graybox.py render / clip / compare──▶ PNG · MP4 · GIF
```

## 실행

```bash
cd pixel-splat            # venv 활성화 상태, PYTHONPATH=.
python examples/map/graybox.py build             # 1~2분 (splat 17만 개, CPU 4코어) → out/map_45
python examples/map/graybox.py render            # overview.png, view_bb.png, bb_closeup.png (5~15초)
python examples/map/graybox.py clip              # walk_follow.mp4 / .gif (프레임당 0.5~0.9초, 371프레임)
python examples/map/graybox.py compare --ref-video <레퍼런스.mp4> --ref-time 15
```

굽는 폴더는 **카메라마다 따로**다: 기본(45°)은 `out/map_45`, `--elev 30`이면 `out/map_30`. 다른 폴더는 `-o`로 고른다(render·clip·compare도 같은 `-o`).
이미 **다른 카메라로 구운** 폴더에 `build`하면 덮어쓰지 않고 멈춘다(바꾸려면 `--force`). 예전 30° 결과가 있는 `out/map`은 그대로 남는다.
내려다보는 각 `--elev`는 5~85°만 받는다(0°는 땅이 안 보이고 해 방향 계산이 0으로 나뉜다).

BB는 `out/bb`(60k splat)를 읽어 1,000개로 솎고 그만큼 키워 쓴다. 인물이 6×16픽셀이라 splat이 전부 래스터 타일 몇 칸에 몰리는데,
래스터 비용은 타일당 splat 수에 비례한다(60k 그대로면 프레임당 10초 이상, 1,000개면 0.5초, 이 크기에서는 그림이 같다). 다른 폴더면 `--bb`.
BB 색은 기본이 단색(따뜻한 점토색)이다. 구울 때의 색을 쓰려면 `--bb-color own`.

## 맵 고치기: `layout.json`

길이는 전부 **미터**, `x` = 동쪽, `z` = 남쪽(카메라 쪽), 높이는 풀밭 기준. 각도는 도(°)이고 +x에서 +z 쪽으로 돈다.
월드 단위는 soldier와 같다(1.80 단위 = 1.75 m, 땅 y = −1). 변환은 `level.UNITS_PER_M`.

| `type` | 뜻 | 값 |
|---|---|---|
| `hill` | 완만한 언덕 | `at`, `radius`, `height` |
| `pond` | 평평하게 꺼진 연못(어두운 면) | `at`, `radius` [rx, rz], `depth`, `bank`(기슭 폭) |
| `plateau` | 절벽으로 둘러싸인 단 | `at`, `size` [가로, 세로], `height`, `rot` |
| `ramp` | 경사로 | `at`, `size` [길이, 폭], `rot`(오르는 방향), `height` [시작, 끝] |
| `path` | 길(땅에 칠한 띠) | `points` [[x,z]…], `width` |
| `spawn` | 스폰 표시(원판 + 바라보는 방향) | `at`, `facing` |
| `rock` | 바위(반 타원체) | `at`, `size` [가로, 높이, 세로], `rot` |
| `tree` | 나무 대역(원기둥 + 원뿔/구) | `at`, `height`, `radius`, `canopy` = `cone`\|`sphere` |

`demo` 항목은 렌더용이다: `stand`(BB가 서는 곳), `walk`(걷는 경로·속도), `compare`(비교 그림에서 서는 곳).
고친 뒤에는 `build`부터 다시 돌린다. 색은 재질과 높이로만 정한다(`level.TONE`, 걸을 수 있는 땅은 1 m 오를 때마다 조금 밝게).
바닥의 눈금은 1 m(굵은 선 5 m)이고 픽셀마다 월드 좌표로 그려서 항상 1픽셀 폭이다. 선의 반폭은 그 픽셀이 덮는 땅의 반이고,
픽셀의 법선으로 계산하므로 경사로·언덕에서도 1픽셀이다(평지 값 하나로 그리면 카메라 쪽 경사로에서 선이 절반쯤 2픽셀이 된다).
x = 0 선은 원점이 픽셀 **모서리**에 고정되어 있어 두 픽셀 한가운데를 지난다. 예전에는 양쪽 픽셀이 둘 다 선으로 칠해져 이 선만 2픽셀이었다
(`out/map_45`: 277·278열이 둘 다 0.74배). 이제 선의 띠를 한쪽만 닫힌 구간으로 두고 음수 쪽으로 아주 조금(반폭의 0.1%) 밀어서,
경계에 걸친 선은 늘 음수 쪽 픽셀 하나만 칠한다(`out/map_45b`: 277열만 0.736배, 41줄 모두 1픽셀).

**`layout.json` 검사.** `build`(그리고 `Level`을 만드는 모든 곳)는 먼저 파일 전체를 검사하고, 틀린 곳을 **한꺼번에** 한국어로 알려 준다 —
몇 번째 요소(`elements[3] (4번째, pond 'pond')`)의 어느 값이 무엇이어야 하는지, 지금 값은 무엇인지. 예:

```
layout.json에 고칠 곳이 2개 있습니다:
  - elements[0] (1번째, hill 'west_rise'): 'radius' 값이 없습니다 — 0보다 큰 숫자를 넣어 주세요
  - elements[5] (6번째, pond 'pond'): 'radius'는 0보다 큰 두 숫자 [a, b](미터)여야 합니다 (지금: 4)
```

잡는 것: 빠진 값, 모양이 틀린 값(쌍 자리에 숫자 하나 등), 0 이하인 크기·높이(음수 `height`의 plateau 포함), 모르는 항목(`"rotation": 45` → "혹시 'rot'?"),
모르는 종류, 맵(`size`) 밖으로 나가는 요소(나무·바위는 반지름까지, plateau·ramp는 돌린 네 모서리까지), 줄기 자리가 없는 구형 나무, `demo`의 맵 밖 점, JSON 문법 오류(몇째 줄).
겹친 언덕은 높이가 **더해지므로** 카메라가 담는 상자(`bounds_world`)도 이제 실제 땅 높이에서 잰다(예전에는 가장 높은 언덕 하나만 봤다).

## 카메라 측정 (레퍼런스 영상 1848×1080, 60 fps, 44.5초)

| 항목 | 값 | 어떻게 쟀나 | 확실한 정도 |
|---|---|---|---|
| 아트 픽셀² 크기 | 영상 8.745 px | 가로·세로 경계 밝기차의 주기(푸리에) — 5개 프레임에서 같은 값 | 측정 |
| 한 화면 | 211.3 × 123.5 아트 픽셀 | 1848/8.745, 1080/8.745 | 측정 |
| 투영 | **직교**(원근 없음) | 카메라가 움직일 때 화면 위쪽 띠와 아래쪽 띠의 땅 흐름 비 = 1.0000 (사분위 0.9988~1.0011, 1,080개 구간). 세로 화각 10°의 원근만 있어도 1.09~1.18이어야 한다 | 측정 |
| 격자 | 월드에 고정 | 격자 위상이 프레임마다 바뀐다 = 저해상도 그림을 통째로 서브픽셀 이동(부드러운 스크롤) | 측정 |
| 내려다보는 각 | **45° (정한 값)** | 측정으로는 정해지지 않았다: 땅 위 단서는 25~36°, 단서 하나는 44~45°(아래 "각도"). 그중 **45°를 쓰기로 정했다**. 30°도 옵션으로 남긴다 | 선택 |
| 사람 크기 | 선 사람 ≈ **16 아트 픽셀** (몸통 폭 6~7) | 15초 프레임의 선 캐릭터(머리 끝~발) | 측정(1프레임), 캐릭터 실제 키는 모름 |
| 배율 | **11.1** 아트 픽셀 / 월드 단위 (11.42 px/m) | 1.75 m BB가 45°에서 대략 16픽셀(가끔 15)이 되도록 맞춤 — 렌더로 확인(아래 "배율") | 위 둘에서 유도 |
| 보이는 땅 | 가로 18.5 m × 깊이 15.4 m | 211/11.42, 124/11.42/sin45° | 유도 |
| 해 | 그림자는 화면 왼쪽 + 약간 아래로, 길이 ≈ 화면에서 기둥 키의 0.89배 | 15초 프레임의 선 캐릭터 그림자(약 12×2 픽셀) | 추정 |

30°로 그리려면 `build --elev 30`(배율은 맞춰 둔 9.6이 저절로 붙는다: BB 16픽셀, 9.87 px/m, 한 화면 21.4 m × 25.1 m; 결과는 `out/map_30`).
30°·45° 말고 다른 각을 주면 두 값 사이를 직선으로 어림한 배율을 쓰고 경고를 낸다 — 잰 값이 아니므로 `render` 뒤 `render.json`의 `figure_px`를 보고 `--px-per-unit`으로 맞춘다.

**배율**³: 선 BB는 같은 키의 막대보다 화면에서 크다. 몸의 앞뒤 두께가 sin(각)만큼 더 보이기 때문인데, 45°에서는 그 몫이 30°보다 크다.
그래서 cos 비율로 옮긴 값(9.6 × cos30°/cos45° = 11.8)이나 앞서 적어 둔 11.3은 크다 — 11.3은 렌더하면 **17~18픽셀**이다.
BB가 서는 자리의 소수 픽셀 위치에 따라 1픽셀씩 달라지므로 12곳(서브픽셀 위치를 고르게)에서 쟀다(평평한 땅, `figure_height_px`):

| 각 | 배율 | BB 키(픽셀), 12곳 (모두 facing 90) | 평균 |
|---|---|---|---|
| 30° | 9.6 | 16 ×9, 17 ×3 | 16.25 |
| 45° | 10.4 | 15 ×10, 16 ×2 | 15.17 |
| 45° | 10.6 | 15 ×9, 16 ×3 (데모 자리는 16) | 15.25 |
| 45° | 10.8 / 10.9 | 15 ×5, 16 ×7 | 15.58 |
| 45° | 11.0 | 15 ×1, 16 ×11 | 15.92 |
| 45° | **11.1** | **16 ×12** | **16.00** |
| 45° | 11.2 | 16 ×9, 17 ×3 | 16.25 |
| 45° | 11.3 | 17 ×11, 18 ×1 (데모 자리는 18) | 17.08 |

11.1은 12곳 모두 16픽셀이고 양옆(11.0, 11.2)도 거의 16이라 가운데 값으로 골랐다. 10.6은 데모 자리 한 곳에서만 16이고 대부분 15다.
위 12곳은 모두 한 방향(facing 90)이다. 자리와 방향을 섞어 25가지로 다시 재면 11.1에서 **16픽셀 21번, 15픽셀 4번**이었다
(15는 몇몇 자리에서 facing 90과 270). 그래서 정확히는 "**대략 16, 가끔 15**"픽셀이다.
`out/` 없이도 도는 테스트(`test_mannequin_extremes_span_about_16_px_at_the_calibrated_cameras`)는 BB 쉬는 자세의 끝점 12개(정수리·뒤통수·발끝·뒤꿈치)를
투영해 화면 높이를 잰다: 45°/11.1에서 8방향 평균 15.41(14.83~15.94; 실제 렌더는 여기에 splat 크기가 더해져 15~16픽셀).

**각도**: 직교 카메라에서는 땅 위의 원이 세로로 sin(각) 만큼 눌려 보인다. 그 눌림을 네 가지로 쟀는데 서로 꼭 맞지는 않는다.

| 단서 | sin(각) | 각 |
|---|---|---|
| 곰이 방향을 바꿀 때 실루엣의 가로 분산 대 세로 분산의 기울기(타원체 근사) | 0.41~0.55 | 25~33° |
| 곰의 땅 위 속도(화면 속도 + 땅 흐름) 분포를 가장 뾰족하게 만드는 값 | 0.59 (군집별로는 0.38~0.58) | 36° (22~35°) |
| 땅에 떨어진 핏자국 분포의 세로/가로 폭 | 0.44~0.48 (초반 작은 무리는 0.6~0.7) | 26~29° |
| 플레이어 질주 속도가 모든 방향에서 같다고 볼 때(카메라 속도의 바깥 테두리) | 0.70 | 44° |

땅 위 단서 세 가지는 25~36°에 모이고, 플레이어 속도 단서는 44°를 가리킨다. 측정만으로는 어느 쪽인지 정할 수 없어서
**45°를 기본값으로 쓰기로 정했다**(측정 결과가 아니라 선택이다). 30°는 `--elev 30 --px-per-unit 9.6`으로 그대로 쓸 수 있다.
레퍼런스가 어떤 엔진으로 만들어졌는지는 알 수 없다.

## 왜 이렇게 만들었나

- **레벨은 학습하지 않는다.** 요소가 전부 수식으로 된 단순한 모양이라 splat을 표면에 **격자로** 직접 놓는다(중심·법선·크기가 수식에서 나온다).
  섞지 않는(hard) 합성은 splat 중심에서 1.41σ 안쪽만 덮는데, 격자 간격 d에 σ = 0.62d면 빈틈이 없다(테스트로 확인).
  같은 조건을 무작위 표본(`SplatModel.from_mesh`)으로 채우려면 splat이 약 5배 필요하다.
- **레벨 G-buffer는 한 번만 그린다.** 직교 카메라는 정수 픽셀만큼 옮겨도 같은 픽셀이 그대로 밀릴 뿐이라(테스트로 확인),
  레벨 전체를 월드에 고정된 격자로 한 장 구워 두고 프레임마다 창만 잘라 쓴다. 카메라가 흘러도 **배경은 절대 자글거리지 않고**
  프레임 비용은 BB와 조명뿐이다. 남는 소수 픽셀은 확대한 뒤에 옮긴다(레퍼런스와 같은 방식).
- **엔진 코드를 그대로 쓴다**: `rasterize`(큰 그림은 256px 조각으로 나눠 호출), 2× 렌더 + 투표(`select_downsample`), `despeckle`,
  `shade` / `postprocess`, `ShadowMap` + `visibility`, BB는 `render_gbuffer_frame`(Almost Pixel Perfect snapping 포함).
  예제에서 따로 한 것은 둘이다: 외곽선(엔진의 깊이차 기준은 낮은 각도로 본 땅 전체에 선을 긋는다 → 접평면 거리 기준),
  SSAO 반경(엔진 기본값은 2단위짜리 모델용 → `gbuf.ssao`를 장면 크기로 호출).

## 벽

해가 화면 오른쪽 조금 뒤에서 비추므로 **카메라 쪽을 향한 절벽 면에는 해가 닿지 않는다**. 하늘빛도 절반만 받아서 예전에는 거의 검었다:
중간값 (34, 35, 41) — 배경 (19, 19, 28)과 거의 같아서 벽이 세상에 뚫린 구멍처럼 보였다. 실제로는 앞의 밝은 풀밭에서 튄 빛이 벽을 비춘다.
그 반사광(`graybox.WALL_BOUNCE` = 0.45, 해의 색 × 재질 색 × 면이 선 정도)을 **절벽 픽셀에만** 더했다. 다른 픽셀은 한 값도 바뀌지 않는다(테스트).

| `out/map_45b` 전체 그림, 중간값 sRGB | 예전 | 지금 |
|---|---|---|
| 카메라 쪽 절벽 면 (4,904픽셀) | (34, 35, 41) | **(75, 75, 81)** |
| 배경 | (19, 19, 28) | (19, 19, 28) |
| 그늘진 풀밭 | (88, 92, 105) | (88, 92, 105) |
| 해 받는 풀밭 | (177, 177, 177) | (177, 177, 177) |
| 나무 줄기 | (25, 26, 30) | (25, 26, 30) |

벽은 이제 배경보다 확실히 밝고 그늘진 땅보다는 조금 어둡다(0.3이면 62, 0.6이면 87 — 그늘진 땅과 같아져 높이차가 덜 읽힌다).

## 맵을 짤 때 알아둘 것 (이 카메라의 성질)
- 높이 h인 물체는 **뒤(북쪽) 땅을 h × 1.0 만큼 가린다**(45° 기준, h / tan 45°; 30°였다면 h × 1.73). 5 m 나무는 뒤쪽 5 m를 덮는다.
  그래도 싸움터 남쪽에는 키 큰 것을 두지 않는 편이 좋다(30°로 그릴 때 데모 지점이 나무에 두 번 가려져 나무를 옮겼다).
- 화면 세로 1픽셀이 땅에서는 1.41픽셀 거리다(가로 11.42 px/m, 깊이 방향 8.07 px/m; 30°라면 2배). 깊이 방향 길·틈은 가로보다 1.4배 넓게 잡아야 같은 굵기로 보인다.
- 해는 레퍼런스 화면에서 읽은 **그림자 모양**(기둥 그림자가 화면에서 기둥 키의 0.89배 왼쪽, 0.08배 아래)으로 정해 두고,
  각도에 맞는 해 방향을 거기서 계산한다(30°: 고도 52°·방위 100°, 45°: 고도 57.7°·방위 97.1°). 각도를 바꿔도 그림자가 화면에서 같은 모양이다.

## 플레이 빌드 (브라우저에서 BB 걸어 보기)

`play.py`가 구운 레벨과 BB를 **브라우저 한 화면짜리 게임**에 필요한 파일로 내보낸다(라이브러리 없이 canvas 2D). 맵과 같은 카메라(45°, 11.1 아트 픽셀/단위, 직교, 월드 고정 격자)에서
BB가 걷고, 가져온 복싱 모션(원투, 스텝 인·아웃)을 한다.

```bash
python examples/map/graybox.py build -o out/map_45b                       # 레벨 굽기 (한 번)
python examples/map/play.py build -o out/play --bake out/map_45b --bb out/bb2   # 레벨 층 + 스프라이트 + 페이지 (약 15분: 1,392프레임, 바쁜 4코어에서 프레임당 0.6초)
python examples/map/play.py build -o out/play --bake out/map_45b --only level,page   # 스프라이트는 두고 다시 (몇 초)
python examples/map/play.py check -o out/play                             # manifest와 파일이 맞는지
```

모션은 기본이 `onetwo=out/onetwo3/5m/clip.npz`, `inout=out/inout3/5m/clip.npz`(`--clip 이름=경로`로 바꿈). 결과 `out/play/`(git에 넣지 않음): `index.html`(페이지 내용만 —
claude.ai Artifact로 올리면 바깥 틀이 붙는다) + `assets/`. 크기 약 1.1 MB(`sprites.png` 500 KB, `sprites_data.png` 292 KB, `manifest.json` 108 KB, `level_depth.png` 89 KB, `level.png` 71 KB, `index.html` 21 KB, `terrain.png` 8 KB).

| 파일 | 내용 | 인코딩 |
|---|---|---|
| `level.png` | 레벨 전체, `graybox.py render`와 같은 그림(눈금·그림자·AO·외곽선) 556×408 | sRGB |
| `level_depth.png` | 픽셀마다 카메라 깊이 + 해 받는지 | R·G = 16비트 깊이(`depth_lo`~`depth_hi`, 65535 = 없음), B = 255 해 / 0 그늘 |
| `terrain.png` | 0.25 m 칸마다 땅 높이 + 걸을 수 있는지 (192×160) | R·G = 높이 mm + 32768, B = 255 걸을 수 있음 |
| `sprites.png` | BB 프레임(투명 배경), 8방향 × (걷기 24 + 원투 72 + 스텝 78) | RGBA |
| `sprites_data.png` | 같은 사각형: 픽셀 깊이 − 발 딛은 점의 깊이, 그림자 | R·G = 깊이차 × 2048 + 32768, B = 255 그림자(평지) |
| `manifest.json` | 카메라(월드 → 픽셀·깊이 3×4), 파일, 인코딩, 프레임 사각형·기준점, 애니메이션(fps, root 이동) | JSON |

**스프라이트를 굽는 법.** 같은 카메라·해·명암으로 평평한 작은 풀밭(`flat_stage`)을 구워 두고, BB(`--bb out/bb2`, 벙어리장갑 손)를 맵 클립과 똑같이 1,000 splat으로 솎아
발 딛은 점을 한 픽셀의 **한가운데**에 세워 그린다(`Stage.frame(..., layers=True)`: 색, 깊이, BB가 덮은 픽셀, 해 가시성). BB 픽셀만 오려 색을, 땅에 생긴 그 그림자를 B 채널에,
BB 픽셀의 깊이에서 발 딛은 점의 깊이를 뺀 값을 R·G에 담는다. 걷기는 `motion.walk_pose`를 제자리 걸음(advance 0)으로 24프레임, 모션은 30 fps(60 fps 클립의 한 칸 건너)이고,
클립의 **수평 root 이동은 빼고** 그린다(몸은 기준점 위에 머묾) — 그 이동은 프레임별 `root` [앞, 옆](m)로 manifest에 넣어 페이지가 그만큼 BB를 옮긴다.
대기 자세는 원투 클립 앞부분의 가드(18프레임)를 15 fps로 왕복 재생한다.

**페이지가 하는 일.**
- 화면: 아트 픽셀을 **정수 배**(최소 2)로 키운다(기기 픽셀 기준 정수, nearest). 보이는 넓이는 화면 크기에서 정한다(휴대폰 390 px 폭이면 약 180 아트 픽셀, 데스크톱 1280×800이면 6배로 약 208×121).
  레벨 그림이 월드 고정이라 어느 창이든 같은 픽셀이다.
- 합성: BB 픽셀은 (발 딛은 점의 깊이 + 그 픽셀의 깊이차)가 레벨 깊이보다 가까울 때만 그린다(0.15단위 여유: 경사에서 발이 묻히지 않게) → 나무·절벽·고원 뒤에서 가려진다.
  그림자는 **평지 가정**: 그림자 픽셀이 기대하는 깊이(발 높이의 평지)와 레벨 깊이가 0.35단위 안이고 해를 받는 땅일 때만 레벨 그림자와 같은 비율(manifest `shadow_ratio`)로 어둡게 한다.
  경사·언덕에서는 근사다(그레이박스라 충분). BB가 레벨 그늘(나무 그림자 등)에 서면 BB 전체를 같은 비율로 어둡게 한다.
- 이동: 화면 기준(위 = 북쪽 −z, 오른쪽 = +x), 초속 1.4 m. 방향은 가까운 45°로 돌린다. 막힌 칸이면 축 하나씩 미끄러진다. 높이는 `terrain`을 쌍선형으로 읽어 경사로·언덕·고원을 따른다.
  걷기 프레임은 **실제로 움직인 거리 ÷ 보폭(1.12 m)** 만큼 넘어간다 — 발이 미끄러지지 않는다.
- 픽셀 고정: BB의 기준점은 투영한 점이 든 **픽셀**에 놓인다(스프라이트를 그 픽셀의 한가운데에 세워 그렸으므로). 카메라는 정수 픽셀로만 움직이고, 플레이어가 한 픽셀 옮기면
  카메라는 그 자리에 머물렀다가 부드럽게(0.22초) 따라간다. 보여 주는 정수는 부드러운 값이 0.75픽셀 넘게 벗어날 때만 바꾼다(히스테리시스) — 일정하게 걸을 때는 카메라와 BB가
  같은 프레임에 같이 한 픽셀씩 움직여 BB가 화면에서 1픽셀씩 떨지 않는다.
- 조작: WASD·방향키, J = 원투, K = 스텝 인·아웃(끝까지 재생 후 대기/걷기로). 터치: 화면 왼쪽을 누른 채 끌면 가상 스틱, 오른쪽 아래 버튼 두 개(원투, 스텝; 76 px).
- 걸을 수 있는 칸(`play.walk_grid`): 맵 가장자리 0.35 m, 이웃 칸과 높이차 0.15 m 넘는 곳의 양쪽 칸(절벽·고원/경사로 옆면 — 경사로 자체는 칸당 0.08 m라 걸을 수 있음),
  물, 나무줄기 반지름 + 0.25 m, 바위 바닥 + 0.15 m는 막힌다. 경사로가 풀밭과 고원을 잇고, 작은 단(ledge)은 사방이 절벽이라 못 올라간다(테스트).

확인(헤드리스 Chromium, 390×844 휴대폰·1280×800 데스크톱): 콘솔 오류 없음, 가로 스크롤 없음, 걷기 1.4 m/s, J·K 동작이 끝까지 재생된 뒤 대기로,
나무 뒤·고원 북쪽 가장자리 뒤에서 BB가 가려짐, 경사로를 따라 높이 0 → 1.6 m로 고원 위까지, 연못 기슭에서 멈춤, 일정하게 걸을 때 BB의 화면 위치 고정(1픽셀 흔들림 0회).

## 한계
- BB는 16픽셀이라 걸을 때 픽셀이 조금씩 바뀐다(snapping으로 줄였을 뿐 없앨 수는 없다). 배경은 고정이다.
- 경사로·언덕 위에서 BB는 골반 위치의 땅 높이만 따라간다(양발이 각각 땅에 붙지는 않는다).
- 카메라 방위(`--az`)는 0만 눈으로 확인했다. 정확히 남쪽에서 볼 때 나무의 좌우 대칭 splat은 깊이가 같아 앞뒤 순서가 임의다(그림에는 영향 없음).
- 눈금·그림자 맵은 `build` 때 굽는다. 해 방향이나 격자를 바꾸면 다시 구워야 한다.
- 플레이 빌드: BB 그림자는 평지 가정(경사·턱에서는 어긋나거나 사라짐), BB가 레벨 그림자에 들어가면 몸 전체가 한꺼번에 어두워진다(부분 그늘 없음).
  걷기 ↔ 가드 ↔ 모션 사이는 섞지 않고 바로 바뀐다. 모션 중 root 이동이 막히면 그 자리에서 재생만 계속한다. 방향은 8개뿐이라 대각선 아닌 입력은 가장 가까운 45°로 돈다.

¹ **그레이박스(gray box, blockout)**: 텍스처 없이 회색 덩어리만으로 맵의 크기·동선·높낮이를 먼저 잡아 보는 단계.
² **아트 픽셀**: 확대하기 전, 저해상도 그림의 픽셀 한 칸.
³ **배율(px_per_unit)**: 월드 길이 1단위가 화면에서 몇 아트 픽셀인지. 카메라를 더 내려다보게(각도↑) 하면 서 있는 물체가 화면에서 짧아지므로, 사람을 같은 16픽셀로 두려면 배율을 키워야 한다.
