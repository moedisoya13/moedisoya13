# 여명 전야 — 회고와 다음 개발을 위한 개선점

작성: 팀장(Claude), 2026-11-18. 작업은 사용자의 결정으로 여기서 멈췄다. 이 문서는 나중에 이 게임을 다시 기획하거나 개발할 사람과 에이전트를 위한 것이다.

## 요약

- **게임은 두 번 다 재미 검증에 실패했다.** v1은 "할 일이 없다"(너무 재미가 없다), v2는 "물량 공세와 반복 노동"이었다. 두 실패는 반대 방향이지만 원인이 같다.
- **근본 원인은 두 가지다.**
  1. 재미 대신 "바쁨"을 재는 지표(분당 처치, 화면 안의 적 수, 선택 간격, 봇 승률)를 성공 기준으로 삼았다.
  2. 사람이 손으로 재미를 확인하기 전에 콘텐츠의 폭을 넓혔다.
- **남길 만한 것도 있다.** 기술 기반(오프라인 단일 HTML, 결정적 시뮬레이션, 테스트·측정 도구, 애니메이션 파이프라인, 로우폴리 무대 키트, 도감)은 그대로 재사용할 수 있다.
- **다음에는 순서를 바꾼다.** 방 하나·적 셋·카드 셋으로 핵심 재미 하나를 사용자 손으로 먼저 확인한다. 그다음에만 넓힌다.

## 2. 사용자 평가와 원인

### v1: "너무 재미가 없다"

v2 기획 에이전트가 사람 같은 봇으로 40판을 재서 원인을 수치로 확인했다.

| 문제 | 측정값 |
|---|---|
| 얻을 것이 없다 | 선택 사이 73초, 첫 선택 47초 |
| 화면이 빈다 | 화면 안의 적 평균 3.7마리 |
| 한 번에 하나만 벤다 | 베기의 83%가 적 하나만 맞힘. 범위 카드가 쓸모없음 |
| 적이 안 죽는다 | 적 하나에 평균 4.3번(암흑기사 16.7번). 봇 승률을 낮추려고 HP를 3배로 올린 결과 |
| 층이 다 같다 | 4층과 1층의 분당 처치 비율 0.92 |

### v2: "물량 공세와 반복 노동"

v1의 진단은 맞았다. 하지만 처방이 반대쪽 끝으로 갔다.

1. **목표 지표가 처리량이었다.** 분당 처치 100 이상, 화면 안의 적 12~40을 통과 기준으로 걸었다. 에이전트들은 이 기준을 맞추려고 등장 속도를 올렸다(분당 처치 194~206). 물량은 설계된 결과다.
2. **과업이 셈하기였다.** "소탕 200/260/330/400/470마리"는 정의부터 반복 노동이다. 수성(40초 버티기), 봉인(5초씩 3번)도 같은 구조다.
3. **성장이 잦은 숫자 팝업이 됐다.** 30초마다 셋 중 하나를 고른다. 대부분 카드 18장 × 5단계와 단련 7종 × 3단계의 수치 증가다. 고르는 행위가 일상 업무가 됐다.
4. **플레이어의 동사가 이동 하나뿐이다.** 자동 공격에 사방에서 오는 떼가 붙으면, 플레이어는 무리를 몰고 빛 조각을 줍는 일을 한다. "카드 세 장이 어디에 설지를 바꾼다"는 이 게임의 고유한 아이디어가 묻혔다. 측정에서도 칼이 닿는 거리 안에 적이 셋 이상인 시간은 18%뿐이었다.
5. **판이 길고 넓어졌다.** 48×48칸 층과 12.5~15.5분 목표 때문에 걷는 시간과 같은 일의 반복이 늘었다. 비행기에서 짧게 하는 게임이라는 목적과 반대다.
6. **위협이 묻혔다.** v1의 개성 있던 적(슬라임의 덮치기, 암흑기사의 돌격)이 잡졸 무리 속 배경이 됐다.

**공통 원인:** "이동만 하고 자동으로 벤다"는 핵심 조작은 결정 밀도의 상한이 낮다. 적이 적으면 할 일이 없고(v1), 적이 많으면 노동이 된다(v2). 밀도 조절로는 이 상한을 넘지 못한다. 개별 적과 상황의 질, 또는 플레이어 동사의 수를 바꿔야 한다.

## 3. 과정 자기 평가

### 잘한 것

- 오프라인 단일 HTML, 결정적 시뮬레이션, `window.__BD` 훅, 봇, 수용 기준 스크립트를 처음부터 넣었다. 모든 변경을 자동으로 확인할 수 있었다.
- 엔진 계약 문서(`ARCHITECTURE.md`) 덕분에 병렬 에이전트의 작업이 큰 충돌 없이 합쳐졌다.
- 조작성 평가가 측정으로 진짜 문제를 찾았다(조이스틱이 3mm, 돌진 입력 씹힘, 예고가 처음 0.1초에 안 보임). 고친 뒤 29개 항목을 모두 통과했다.
- 영상 생성 → 프레임 추출 파이프라인으로 원래 그림의 화풍을 유지한 애니메이션 13개를 만들었다.
- 사용자가 실제 폰에서 찾은 회전 안내 버그를 빨리 고쳤다(화면을 90° 돌려 그리기).

### 잘못한 것 (팀장으로서)

1. **재미를 지표로 대신했다.** 봇 승률과 분당 처치가 목표 안에 들어오면 "성공"이라고 보고했다. "내가 이걸 열 번 하고 싶은가"를 묻지 않았다. 지표가 목표가 되자 에이전트들은 지표를 맞췄다.
2. **검증 전에 확장했다.** v2 증명 조각의 관문은 숫자였다. 숫자를 통과하자마자 에이전트 넷(카드 18장×5단계, 적, 층 5종, 화면)을 병렬로 띄웠다. 사용자가 조각을 해 보고 판정을 내리기 전에 대부분의 작업이 끝나 있었다.
3. **"직접 플레이"를 봇으로 대신했다.** 사용자는 "직접 플레이하며 자기 개선"을 요청했다. 나는 손으로 플레이할 수 없다는 한계를 밝히지 않고 봇과 캡처로 근사했다. 사람 같은 봇은 생존을 재는 모델이지 즐거움을 재지 않는다.
4. **범위가 팽창했다.** 주말 게임잼에서 출발했는데 끝에는 카드 90단계, 단련 21단계, 과업 5종, 배치 5종, 소품 26종, 4MB 파일, 테스트 332개가 됐다. 변경 하나가 느려지고 튜닝이 깨지기 쉬워졌다. 세 브랜치가 따로 튜닝해서 사람 같은 봇 승률이 12%, 25%, 42%로 갈렸다.
5. **숫자로 설계를 덮었다.** v1에서는 적 HP를 3배로 올렸다가 2/3로 내렸다. v2에서는 적 피해 배율을 최대 ×3.1, 마왕 공격을 ×2로 올렸다. 숫자를 크게 움직여야 맞는다는 것은 설계가 버티지 못한다는 신호였는데, 그렇게 읽지 않았다.
6. **요청을 한 번 거꾸로 이해했다.** "인게임 갑옷 단순화"를 컨셉 원화 편집으로 처리해 크레딧을 낭비했다.
7. **실기기 검증이 없었다.** 목표는 비행기 안 휴대폰인데 끝까지 실제 기기에서 돌려 보지 못했다. 60fps도 휴대폰에서는 확인되지 않았다.
8. **피드백 주기가 길었다.** 에이전트 작업 하나가 1~2시간이었고, 사용량 한도와 컨테이너 재시작으로 여러 번 멈췄다. 사용자가 결과를 보는 간격이 길어졌다.

## 4. 다음 개발을 위한 개선점

### A. 기획

1. **한 문장 재미 가설부터 정하고, 그것을 깨는 실험을 먼저 한다.** 이번 작업에서 가장 고유하고 살아 있던 가설은 "무작위로 받은 카드 세 장이 '어디에 서야 하는가'를 판마다 바꾼다"였다. 이것을 지키고 물량은 버린다.
2. **적은 적게, 서로 다르게.** 화면에 위협 2~6마리를 두고, 각자가 다른 위치 판단을 요구하게 한다. 잡졸 물량 대신 설계된 조우(방 하나가 작은 퍼즐 하나)를 시드로 변주한다.
3. **플레이어의 동사를 하나 더 검토한다.** 이동만으로는 결정 밀도의 상한이 낮다(§2 공통 원인). 선택지:
   - (a) 버튼 하나로 카드 하나를 발동(재사용 대기)
   - (b) 자동 공격 방향을 잠그거나 푸는 조작
   - (c) 원래 초안(턴제·격자, `docs/prior/design-draft4-turn-based.md`)으로 돌아가기

   실시간·자동 공격은 사용자가 고른 방향이므로 사용자와 함께 고른다.
4. **성장은 숫자 사다리 대신 질적 변화로.** 판당 2~4번의 큰 선택(제단, 퀘스트 각성, 콤보의 성질 변화)이 30초마다 오는 수치 +10%보다 낫다. v1의 퀘스트·콤보 카드가 이 역할을 했다.
5. **과업은 셈하기 대신 상황으로.** "N마리 처치", "N초 버티기"를 금지한다. 층이나 방마다 하나의 상황(호위, 탈출, 매복, 보스 패턴 읽기)을 두고, 상황이 풀리면 끝낸다.
6. **판은 짧게.** 비행기라면 8~12분, 짧은 방 여러 개가 맞다. 여명 시계는 남은 방 수와 맞물린 압박 장치로 다시 설계한다.

### B. 검증 방법

1. **사용자 플레이테스트를 관문으로 삼는다.** 반복마다 5분 분량의 빌드를 주고 세 가지를 묻는다: 가장 재미있던 순간, 지루했던 순간, 다시 할 이유. 답을 받기 전에는 넓히지 않는다.
2. **경험을 재는 지표를 쓴다.**
   - 의미 있는 결정의 수: 서로 다른 결과를 내는 자리가 둘 이상인 순간
   - 긴장 곡선: 위험과 휴식의 리듬
   - 판 안에서 만난 상황의 종류 수
   - 같은 행동을 반복한 시간

   분당 처치 같은 처리량은 "이 이상이면 노동"이라는 상한으로만 쓴다.
3. **봇은 안전망으로만 쓴다.** 회귀와 밸런스 이상치를 잡는 데 쓰고, 재미 판정에 쓰지 않는다.
4. **첫 빌드부터 실제 휴대폰에서 돌린다.** 성능, 터치, 회전을 확인한다.

### C. 개발 과정

1. **작은 핵심 → 사용자 확인 → 확장.** 병렬 에이전트는 핵심이 사용자 손으로 검증된 뒤에만 쓴다.
2. **수치 담당은 한 명.** 병렬 브랜치에서 각자 튜닝하지 않는다.
3. **범위 상한을 기획서 단계에서 고정한다.** 예: 카드 10장 이하, 적 6종 이하, 층 유형 3종 이하. 넘기려면 사용자 승인을 받는다.
4. **작업을 작게 쪼갠다.** 에이전트 작업 하나를 30~60분 이하로 나눠 사용자가 자주 본다.
5. **팀장은 지표 통과를 "성공"으로 보고하지 않는다.** "지표는 통과, 재미는 미검증"으로 구분해 쓴다.
