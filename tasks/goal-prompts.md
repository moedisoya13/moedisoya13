# `/goal` 조건문 — 쿠팡 판매가 수집 (모바일 경로)

`/goal`은 **Claude Code 기본 명령어**입니다. 완료 조건을 걸면, 매 턴이 끝날 때마다 별도의
작은 모델이 그 조건이 충족됐는지 판정하고, 아니면 Claude가 스스로 다음 턴을 시작합니다.
조건이 충족되면 goal은 자동으로 해제됩니다.

> 이 저장소에 `.claude/commands/goal.md`를 **만들지 마세요.** 동명 파일은 기본 명령어를 가립니다.

```
/goal <조건>     조건을 걸고 즉시 한 턴 시작 (조건 자체가 지시문이 됨)
/goal            현재 상태 — 조건·경과 시간·턴 수·토큰·평가자의 최근 이유
/goal clear      해제 (stop·off·reset·none·cancel도 같음)
```

---

## 조건을 쓸 때의 원칙

**평가자는 도구를 쓰지 않습니다.** 명령을 돌리지도, 파일을 읽지도 않고 **대화에 이미 드러난
것만** 보고 판정합니다. 이 한 가지가 조건 설계를 전부 좌우합니다.

| 원칙 | 이유 |
|---|---|
| 종료 근거를 **명령어 출력**으로 쓴다 | `npm test가 28 pass를 출력했다` ○ / `단축어가 잘 동작한다` ✗ |
| **턴 상한**을 넣는다 (`또는 N턴이 지나면 중단`) | 공식 문서 권장. 폭주를 막는 유일한 장치 |
| **사람 대기 탈출구**를 넣는다 | 이 프로젝트의 남은 일은 사람 손이 있어야 끝납니다. 없으면 조건이 영원히 충족되지 않아 **토큰만 태웁니다** |
| 바꾸면 안 되는 것을 **제약으로 명시** | 좋은 조건의 3요소: 측정 가능한 종료 상태 · 증명 방법 · 지켜야 할 제약 |
| 무인 실행이 필요하면 auto mode와 병행 | `/goal`은 **권한을 바꾸지 않습니다.** 기본 모드에서는 도구마다 계속 물어봅니다 |

조건은 최대 4,000자, 세션당 1개입니다.

**쓰기 전 확인**: `/goal`은 v2.1.139+ 이고, 신뢰 대화상자를 수락한 작업공간에서만 됩니다
(평가자가 훅 시스템의 일부라서). `disableAllHooks`가 켜져 있으면 안 됩니다.

## G1 — 키트 상태 재검증 (세션을 새로 열었을 때)

Track A가 여전히 성한지 한 번에 확인합니다. 키트를 고친 뒤에도 씁니다.

```
/goal 다음 네 가지가 모두 대화에 출력으로 증명되면 완료: (1) mobile-collect/ 가 현재 브랜치에
있고 git status가 clean, (2) cd mobile-collect && npm test 가 30건 이상 pass·0 fail 출력,
(3) npm run check:snippet 과 npm run check:markers 가 둘 다 최신 상태 확인 메시지로 종료,
(4) 루트 npm test 48 pass 와 npm run type-check 무오류. 제약: extract.js의 BLOCK_MARKERS 값을
바꾸지 말 것, shortcut/run-javascript-body.js 와 pc-side/markers.json 을 손으로 고치지 말 것
(생성기로만), 실물 픽스처 없이 parse 규칙을 새로 넣지 말 것, 루트 src/ 를 건드리지 말 것.
판단이 갈리는 지점을 만나면 추측하지 말고 질문을 남기고 멈출 것 — 질문을 남긴 경우도 완료로
본다. 또는 15턴이 지나면 중단.
```

## G2 — PC측 확인 1~3 (쿠팡 `NewPipe` 저장소에서)

```
/goal python mobile-collect/pc-side/check_pc_side.py 가 종료코드 0으로 끝난 출력이 대화에 있으면
완료. 확인 1·2에서 조치가 필요하다고 나오면 그 지목된 곳을 고친 뒤 다시 돌리고, 그 다음
python -m pytest coupang_crawler -q 가 324건 이상 pass를 출력해야 한다. 제약: 실물 모바일
픽스처가 커밋되기 전에는 parse.py의 SELLER_SECTION_MARKERS나 옵션 라벨 후보를 절대 바꾸지 말 것
(버그 #3 재발 경로), 구간을 못 찾으면 빈 리스트를 반환하는 현재 정책을 유지할 것, receiver.py의
127.0.0.1 바인딩을 바꾸지 말 것, 확인 1에서 상품명 기준으로 판명되면 Python을 고치기 전에 단축어
매핑(ⓐ)과 config.py 재사용(ⓑ) 중 어느 쪽인지 먼저 물어볼 것. 실물 픽스처가 없어서 확인 4·5로
못 넘어가는 상태에 도달하면 그 사실을 보고하고 멈출 것 — 그것도 완료로 본다. 또는 20턴이 지나면
중단.
```

## G3 — 파서 교정 (실물 픽스처가 생긴 뒤에만)

```
/goal tests/fixtures/의 실물 모바일 픽스처로 parse.py의 옵션·판매자 추출을 검증하는 pytest가
추가되어 전체 pass를 출력하고, 그 픽스처에서 뽑힌 CSV 행이 대화에 인쇄되어 option에 판매자명이
없고 seller에 상품명이 없으며 price가 와우 회원가·쿠폰적용가와 구분되어 있음이 확인되면 완료.
제약: 픽스처는 받은 그대로 유지할 것(개인정보 제거 외 편집 금지), 구간 미발견 시 빈 리스트 반환
정책을 유지할 것, 차단 마커를 고쳤다면 extract.js·tests/extract.test.mjs의 고정 테스트·
npm run build:snippet·npm run dump:markers 를 함께 갱신할 것. 실물 픽스처가 아직 없으면 즉시 그
사실만 보고하고 멈출 것 — 그것도 완료로 본다. 또는 20턴이 지나면 중단.
```

## 운용 메모

- **순서**: G1 → (사용자가 B-1 수행) → G2 → (B-2 픽스처 커밋) → G3.
  세션당 goal은 1개이므로 **세션을 갈아 가며** 씁니다.
- **`/goal`로 수집 자체를 돌리지 마세요.** 사람이 폰에서 탭할 때만 읽는다는 전제를 깨는
  방향입니다. 그리고 `blocked`일 때 재시도하지 않는 규칙은 사람이 지켜야 합니다.
- 무인으로 돌리려면 auto mode와 함께 씁니다. 다만 위 세 조건은 전부
  **파괴적이지 않은 명령**(테스트·타입체크·읽기 전용 스크립트)만 근거로 삼습니다.
- 진행이 이상하면 `/goal`을 인자 없이 쳐서 **평가자의 최근 이유**를 보세요.
  Claude가 다음 턴에 무엇을 하려는지가 거기 적혀 있습니다.
- 조건을 잘못 걸었다 싶으면 새 조건으로 `/goal`을 다시 치면 **교체**됩니다.

## 흔한 실패 조건 (쓰지 말 것)

| 나쁜 조건 | 왜 |
|---|---|
| `단축어가 정상 동작하면 완료` | 평가자가 확인할 방법이 없다. 사람 폰에서만 알 수 있다 |
| `CSV가 잘 쌓이면 완료` | "잘"이 측정 불가. 어떤 출력으로 증명하는지 없음 |
| `모든 테스트를 통과할 때까지` (상한 없음) | 실패가 환경 탓이면 무한 루프 |
| `파서를 모바일에 맞게 고칠 것` | 실물 픽스처 전에는 **해서는 안 되는 일**이다 |
